## 二、面试推荐版简历

> **核心改动思路**：5 条精华项压缩为 4 条，每条必有可量化数据或可追问的技术决策。ClickHouse/Jaeger/Docker 等不熟的内容降级为从属描述。

---

**NexusLink｜基于 Go Micro 的高性能短链接与实时分析系统**

**项目介绍：** 面向营销投放与社媒传播场景，提供短链生成、高并发跳转与点击实时分析能力。系统重点解决百亿级短码唯一性生成、高并发下低延迟跳转，以及分析链路与核心跳转路径的解耦问题。

**技术栈：** Go · Gin · Go-Micro · NATS JetStream · PostgreSQL · Redis · ClickHouse · Prometheus · Jaeger · Docker Compose

**核心工作与成果：**

- **微服务分层与异步解耦设计：** 按读写特征拆分 URL 生成、Redirect 跳转、Analytics 分析、API 网关四个独立服务，通过 NATS 作为 RPC 传输层保障内网高效通信。跳转服务仅负责 302 重定向，点击事件通过 goroutine 异步投递至 NATS JetStream，由 Analytics 服务消费后批量写入 ClickHouse，实现分析链路对跳转主路径**零阻塞**。

- **多级缓存与防穿透体系（核心亮点）：** 针对读多写少场景，自研五级缓存防护链路：「L1 本地内存缓存 → 基于 Redis Bitmap 的布隆过滤器（Kirsch-Mitzenmacher 双散列）→ Singleflight 防击穿合并 → Redis L2 缓存 → PostgreSQL 终态回源」。基于 Prometheus 对各级命中率实时埋点监控，通过 4 轮性能瓶颈定位与调优，**QPS 从 1,676 提升至 5,535（3.3 倍）**，L1 命中率 99.6%，TTFB 3.72ms，短码冲突率 0%。

- **防枚举的分布式短码生成：** 基于 Redis INCR 原子计数器分配全局唯一 ID，结合**自定义乱序 Base62 字符表置换**生成短码，在保证 0% 冲突率的同时阻断竞品对业务单量的枚举扫描。支持自定义别名（Alias）与过期自动清理，通过数据库唯一约束解决别名与系统码的命名空间冲突。

- **可观测性与性能调优实战：** 接入 Prometheus 采集 QPS、多级缓存命中率、连接池水位等自定义指标并通过 Grafana 可视化；集成 Jaeger 实现跨服务分布式追踪。在压测过程中排查出 Go-Micro 框架配置覆盖导致的 NATS 传输层丢失、跨服务 JSON 时间戳序列化不兼容导致的 L2 缓存 0% 命中、PostgreSQL 行锁竞争、以及冗余 RPC 调用翻倍 NATS 流量等隐蔽性能问题。

## 三、面试高频问题与回答策略

> **原则**：对每个问题，先给 30 秒的"表面回答"，再准备 1-2 分钟的"深挖回答"。对不熟的领域（ClickHouse/Jaeger），给出框架性认知后主动收住，把话题引向你擅长的缓存和并发。

### A. 架构设计类（必问）

**Q1：为什么跳转和短链生成要拆成两个服务？**
> 核心是读写 TPS 差异。跳转是极高频读（每秒几千次）且无状态，短链生成是相对低频写（涉及 DB 唯一性校验）。拆分后可以为 Redirect 服务单独分配更多实例做水平扩展，而且写服务的故障或 OOM 不会拖垮核心跳转。

**Q2：为什么用 302 不用 301？**
> 301 是永久重定向，浏览器会缓存到本地。下次用户再点短链时直接跳走，请求不经过我们的服务器，导致**点击统计数据完全丢失**。用 302 保证每次点击必须经过服务器，这是短链系统的核心商业需求。

**Q3：NATS 作为 RPC 传输层而不是用 gRPC 直连，为什么？**
> Go-Micro 框架原生支持插件式 Transport。使用 NATS 作为传输层的好处是：① 天然自带服务注册与发现（NATS Registry），省去 Consul/Etcd 的部署成本；② NATS 的发布-订阅模型天然支持负载均衡；③ 同一套 NATS 既做 RPC 传输又做事件总线发布点击事件，架构统一。

### B. 多级缓存类（⭐ 重点深挖区）

**Q4：描述一下短链跳转的完整链路。**
> 请求进入 Gin 路由 → rest-api-svc 通过 NATS RPC 调用 redirect-svc → redirect-svc 的 store 层按序检查：
> 1. **L1 本地缓存**（go-cache，微秒级）→ 命中率 99.6%，绝大部分请求到此结束
> 2. **Redis 布隆过滤器** → 如果短码不在 Bloom 中，直接返回 404，拦截恶意穿透
> 3. **Singleflight** → 相同短码的并发请求合并为一次远程查询，防止缓存击穿雪崩
> 4. **Redis L2 缓存** → 命中则回填 L1
> 5. **PostgreSQL** → 终态回源，查到后同时回填 L2 和 L1
> 
> 查到后返回 302，同时 goroutine 异步发布点击事件到 NATS。

**Q5：布隆过滤器是调的库还是自己实现的？底层原理是什么？**
> 自己实现的。基于 Redis 的 `SETBIT` / `GETBIT` 命令操作一个 1 亿位的 Bitmap。使用 **Kirsch-Mitzenmacher 双散列优化**，只需计算两个基础哈希值 h1 和 h2，第 i 个哈希函数的偏移量为 `(h1 + i*h2) % m`，用 5 个哈希函数实现低于 1% 的误判率。添加和查询都用 Redis Pipeline 批量执行，减少网络往返。

**Q6：Singleflight 的底层怎么实现的？**
> 核心是一个 `sync.Mutex` 保护的 `map[string]*call`。第一个请求进来，在 map 中注册一个 call 并开始执行查询；后续相同 key 的请求看到 call 已存在，就通过 `sync.WaitGroup.Wait()` 挂起等待。第一个请求完成后 `wg.Done()`，唤醒所有等待者共享同一个结果。这样 1000 个并发只产生 1 次 DB 查询。

**Q7：L1 和 L2 之间的一致性怎么保证？**
> 短链接场景是"创建后基本不修改"的，所以 L1 设置了 10 分钟 TTL，到期被动淘汰。如果需要主动失效（如封禁违规链接），可以通过 Redis Pub/Sub 广播 invalidate 消息给所有 Redirect 实例清除本地缓存。

### C. 短码生成类（⭐ 常被追问）

**Q8：为什么不用 UUID 或 Snowflake？**
> 短链要求 6-7 位以内，UUID 太长。Snowflake 生成的是 64 位整数，直接取前几位做 Hash **一定会冲突**，遇到冲突就要循环查库重试，高并发下性能不可接受。而 Base62 编码 62^6 ≈ 560 亿个无冲突映射空间，用 Redis INCR 原子递增恰好是最简洁的无碰撞方案。

**Q9：Redis INCR 挂了怎么办？**
> 可以采用**预分配号段**机制：每次从 Redis 批量拿 1000 个 ID 缓存在内存里，内存发完再取下一批。这样即使 Redis 短暂宕机，内存中还有余量，且 Redis 重启后 AOF 持久化可恢复上次的计数值。即使丢了几万个 ID 也只是跳号，不会重复。

**Q10：怎么防止竞品通过短码枚举你的业务量？**
> 普通的 `INCR → Base62` 是顺序的（1→a, 2→b），完全可以被枚举。我使用了**自定义乱序字符表**：把标准的 `0-9a-zA-Z` 打乱成一个秘密排列（相当于一个简单的置换密码），这样即使 ID 是递增的，编码出来的短码在外部看起来完全无规律。字符表就是密钥，不泄露就无法反推。

**Q11：自定义别名和系统生成的短码会冲突吗？**
> 两种策略：① 长度隔离——系统生成固定 6 位，自定义别名限制 8 位以上；② 数据库唯一约束——先用 `INSERT ... ON CONFLICT` 插入，如果触发唯一索引冲突就返回"别名已存在"。我的代码里两种都实现了。

### D. 异步解耦与 NATS（中频考点）

**Q12：为什么选 NATS JetStream 而不是 Kafka？**
> 两者都能做持久化。NATS 用 Go 编写，轻量级，单二进制部署，不需要 ZooKeeper 等依赖。对于这种事件量级（每秒几千条点击流水），NATS JetStream 的 At-least-once 投递完全足够，运维成本远低于 Kafka 集群。

**Q13：投递失败会影响跳转吗？**
> 不会。投递是在 goroutine 中异步执行的，跳转主线程不等待投递结果。即使 NATS 完全不可用，用户依然能正常302跳转，只是这段时间的点击数据会丢失。我们可以容忍分析数据的少量丢失，但不能容忍跳转主路径被阻塞。

### E. 性能优化故事（⭐⭐ 面试必杀技）

**Q14：说说你在这个项目中遇到最大的技术挑战？**

> （选"QPS 优化全过程"讲，这是最完整的故事。）
>
> "压测时发现 QPS 只有 1,676，但 CPU 和内存水位不高，说明存在 I/O 阻塞。我做了四轮排查：
>
> **第一轮**，发现连接池参数配置有个框架陷阱：我在 Go-Micro 初始化时用 `micro.Client(client.NewClient(...))` 传入了新客户端来增加连接池，结果把之前注入的 NATS Transport 全部覆盖了，导致微服务间 RPC 退化为本地 TCP，在 Docker 容器间完全不可达。改为 `service.Client().Init()` 安全追加后恢复。
>
> **第二轮**，排查 L2 缓存命中率始终 0%。最终发现是 url-shortener-svc 写缓存时用 Unix 时间戳整型，redirect-svc 读缓存时期望 RFC3339 字符串，`json.Unmarshal` 静默失败。同时发现每次重定向都同步执行 `UPDATE click_count` 的 SQL，400 并发下同一行数据的行锁竞争把连接池打满了。时间戳改为 RFC3339 统一格式，UPDATE 改为 Redis INCR + NATS 异步。
>
> **第三轮**，Jaeger 100% 全量采样在高并发下大量协程阻塞在 gRPC IO 上。加上热路径中遗留的十几处 `fmt.Printf` 调试输出（stdout 是带全局锁的系统调用），成为隐形瓶颈。采样率降至 1%，删除所有 Printf。
>
> **第四轮**提升最大。我梳理完整链路后发现，每次重定向触发了 3 次 NATS 操作，其中 rest-api-svc 的 TrackClick RPC 和 redirect-svc 内部的 publishClickEvent 功能完全重复。删除冗余 RPC 后，NATS 流量减半，QPS 从 2,943 跃升到 5,535。"

### F. ClickHouse / Jaeger 相关（低频但要准备框架性回答）

> **策略**：给出 1-2 句框架性回答后，主动把话题引回你擅长的领域。

**Q15：ClickHouse 怎么防止小批量写入导致的 Too many parts？**
> Analytics 服务消费 NATS 消息时不是逐条写入，而是在内存中攒批，达到一定数量或一定时间间隔后执行一次批量 INSERT。ClickHouse 适合大批次低频写入，不适合高频小批量。

**Q16：Jaeger 的 Trace 怎么跨 NATS 传递？**
> 在发送 NATS 消息时，把当前 context 中的 Trace ID 通过 `propagation.Inject` 序列化到消息 Header 中；消费端通过 `propagation.Extract` 反序列化还原 context，这样在 Jaeger UI 上就能看到完整的跨服务调用链。

## 五、同步与异步处理边界分析（重要考点）

面试官常问："哪些操作是必须要同步等结果的？哪些是可以丢进后台做的？"

### 1. 同步流程 (Synchronous Paths)
> **原则**：直接影响用户拿到重定向目标或创建结果的操作，必须同步。

- **重定向链路**：
    1. HTTP 网关接收请求 → RPC 调用 `ResolveURL`。
    2. 多级缓存逐级查找 (L1 -> Bloom -> L2 -> DB)。
    3. `302/404/expired` 状态判断。
    4. HTTP Response 写入 302 Header。
- **生成链路**：
    1. 唯一性 ID 生成 (Redis INCR)。
    2. 短码转换 (Base62)。
    3. 写入数据库存根。

### 2. 异步流程 (Asynchronous Paths)
> **原则**：非核心跳转路径、允许短暂延迟的数据、辅助统计分析，全部异步。

- **点击追踪**：`redirect-svc` 返回 302 后，触发 `go publishClickEvent` 发往 NATS，跳转主流程不等待投递成功。
- **冷热降级**：分析服务从 NATS 消费后根据策略写入 ClickHouse，支持"慢查询"离线分析。
- **指标采集**：Prometheus 埋点是通过后台协程上报或等待 Pull，不占用请求周期毫秒数。

## 六、连接池与并发细节深挖

### Q17：你的 Redis 和 DB 连接池大小是怎么定的？只写 100 够吗？
> **回答策略**：不要回答一个死数字，要回答**计算逻辑**。
> "在压测 400 并发时，连接池设为 100 是一个平衡点。公式通常是：`(预期并发 / 单核吞吐) * 冗余系数`。因为 Go 是协程并发，400 并发并不意味着需要 400 个 TCP 连接，因为绝大部分请求在微秒级就处理完释放回池子了。100 个活跃连接在高频重用下足以支撑数千 QPS。如果连接池太大会导致数据库 FD (文件句柄) 耗尽，太小会产生大量 `connection wait`。"

### Q18：如果连接池爆了会发生什么？怎么解决？
> **回答策略**：
> "会出现 `connection pool timeout`。第一个解决手段是**监控告警**（Prometheus 观察活跃连接数指标），第二个手段是设置合理的 `WaitTimeout` 避免请求无限堆积。底层解决是增加 `MaxOpenConns` 或**服务水平扩容**（分摊到多个 Redirect 实例节点）。"

### Q19：有没有遇到连接泄露 (Connection Leak)？
> **回答策略**：
> "在开发初期遇到过。在 Go 调用 `sql.Rows` 后忘记 `defer rows.Close()`，或者在报错分支出口没关闭连接，导致连接被占着不还，池子迅速被打满。后来通过在代码规范层面强制使用 `defer` 以及使用像 `sqlx` 这样封装较好的库来规避。"

### Q20：Redis 的池化 (Pooling) 和 gRPC 的连接池有什么区别？
> **回答策略**：
> "Redis 协议是单连接单请求响应模式，高度依赖连接池分发 TCP 链路。而 **gRPC 基于 HTTP/2，自带了多路复用 (Multiplexing)**，理论上一个 TCP 物理连接可以并发运行多个 Stream 请求。但在极高并发下，为了避免 TCP 层面的缓冲区瓶颈和锁竞争，我们依然会配置多连接池（PoolSize=200），通过负载均衡到多个 NATS 或服务实例。"

## 七、架构澄清：gRPC 与 NATS 的关系

面试官可能会问："你简历里写了 gRPC 又写了 NATS，到底用的是哪个？"

### 1. 核心结论
项目中**真正运行的传输协议是 NATS**，而不是标准的 gRPC。但由于使用了 **Protobuf (IDL)** 定义接口，所以保留了 gRPC 的开发体验。

### 2. 它们是怎么结合的？
- **Protobuf (gRPC 的语言)**：我们编写 `.proto` 文件，定义 Request 和 Response。这是微服务间的"合同"。
- **Go-Micro (中间件)**：它像是一个底座，它支持"插件"。
    - 如果插上 gRPC 插件，就是标准的 gRPC 通信。
    - 如果插上 **NATS 插件**（本项目做法），就是把 Protobuf 序列化后的二进制流，通过 NATS 的消息管道进行传输。

### 3. 为什么要用 NATS 顶替 gRPC？(面试加分点)
- **解耦性能更强**：gRPC 是点对点的强实时连接，如果下游挂了，上游必须处理重连或报错。NATS 是基于消息队列的，具备**消息缓冲**能力。
- **天然的服务发现**：标准的 gRPC 需要配合 Consul/Etcd。NATS 本身就是注册中心，服务启动后直接往 NATS 注册 Topic 即可，架构更扁平。
- **一物双用**：NATS 既承担了微服务之间的 **RPC 同步调用**（Request/Response），又承担了点击事件的 **异步发布订阅**（Broker），减少了依赖的中间件数量。
