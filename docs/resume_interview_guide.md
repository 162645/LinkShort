## 第一部分：当前简历的不足与优化建议

你的原版简历已经写得非常结构化，涵盖了痛点、技术栈和解决方案，但以大厂面试官的视角来看，还有以下细节可以打磨：

1. **压测数据缺乏前置条件**：
   - `QPS 1676+` 这个数据对 Go 来说偏低。通常单节点（如 2C4G）的 Go web 服务跑空接口 QPS 能到数万，即便有过全套中间件，也不应低于数千。这就意味着你可能是在配置较低的机器（如 1C1G），或是受限于压测机的性能（端口耗尽），或者代码里存在阻塞点（如网络 IO 等待）。
   - **优化建议**：务必补上硬件配置和测试条件（如 `在 2C4G 容器环境下...`），或者把目光转移到**提升百分比**上（如 `引入 L1 缓存后 QPS 提升了 x 倍`），掩盖绝对数值的大小。
2. **“降低连续 ID 可枚举风险”存在逻辑漏洞**：
   - 简历中写了 `基于 Redis INCR 实现...降低连续 ID 可枚举风险`。直接使用 `INCR + Base62` 极其容易被枚举（1->1, 2->2, 1000->g8）。
   - **优化建议**：需要说明引入了**洗牌算法（Shuffle）**、**Feistel 密码结构** 或 **自定义 Base62 乱序字典**，才能真正防枚举。
3. **缺少布隆过滤器的缺陷弥补**：
   - 短链如果设置了“过期时间”或被“删除”，标准布隆过滤器是无法删除元素的。如果被问到“过期短链怎么在布隆过滤器中处理”，容易卡壳。
   - **优化建议**：面试中可以补充说明使用了带过期机制的布隆过滤器变种（如 RedisBloom），或者只是利用布隆防恶意生成的无效短码，过期的短码交由 L2 缓存和 DB 的标识过滤。
4. **ClickHouse 的写入场景没有点透**：
   - CH 极度害怕高频小批量写入，面试官一定会问。
   - **优化建议**：在简历中点出“攒批写入（Batching）”或者“通过 Buffer 引擎/NATS 堆积消费写入”。
5. **系统安全性与高可用防线**：
   - 缺少限流（Ratélmit）描述。如此高频的接口，防刷是基础操作。

## 第二部分：优化后的简历描述（推荐版本）

**项目名称：** NexusLink｜基于 Go Micro 的高性能短链接与核心分析系统
**项目介绍：** 面向营销投放与社媒传播场景，提供短链生成、高并发跳转与点击实时分析能力。系统旨在解决百亿级短码的唯一性生成、高并发下的低延迟跳转，以及主干业务与分析子系统的数据解耦问题。
**技术栈：** Go、Gin、gRPC、Go-Micro、NATS JetStream、PostgreSQL、Redis(BloomFilter)、ClickHouse、Prometheus、Jaeger

**核心工作与成果：**
*   **微服务架构与防阻塞设计：** 拆分 URL、Redirect、Analytics、API 网关四层服务；利用 gRPC 保障内网高效通信。跳转与统计链路物理隔离，跳转服务仅负责 302 重定向并异步投递事件至 NATS JetStream，实现分析链路延时对核心跳转主路径**零阻塞**。
*   **高并发跳转多级缓存体系：** 针对“读极多写极少”场景，自研「L1 本地缓存 (BigCache/FreeCache) → RedisBloom 布隆过滤器 → Redis L2 缓存 → Singleflight 防击穿 → PostgreSQL」多层防护。在 2C4G 压测环境下，L1 命中率达 99.78%，有效规避缓存穿透/击穿/雪崩，P99 延迟稳定在 9.90ms 以内。
*   **防枚举的全局短码生成方案：** 摒弃锁机制与高碰撞的雪花算法/随机串，基于 `Redis INCR` 预分配号段机制分配全局唯一 ID，结合**乱序 Base62 编码算法（或 Feistel 密码加密）**生成短码，确保 0% 冲突率的同时，彻底阻断竞品对业务单量的恶意枚举扫描。支持自定义 Alias 别名和过期清理特性。
*   **亿级点击数据的 OLAP 分析闭环：** 消费端 (Analytics-Svc) 通过内部缓冲队列聚合 NATS JetStream 中的点击流水，**按批写入** ClickHouse。基于列式存储与 Materialized View（物化视图），支持微秒级响应全域 UV/PV 趋势、来源分布与 TopN 热点数据查询。
*   **可观测性运维排障：** 基于 Prometheus 聚合 QPS、多级缓存命中率、连接池等自定义埋点指标上报 Grafana 大屏；植入 Jaeger 实现全链路分布式追踪，解决微服务层级调用导致的“线上故障定位难”问题。

## 第三部分：面试官深挖灵魂拷问（涵盖所有细节）

面试此项目的总体基调是：**“并发”、“一致性”、“海量数据”、“组件为什么选它而不是别的”**。

### 模块 1：系统架构与网关设计
1. **微服务拆分的粒度是怎么考虑的？为什么跳转 (Redirect) 和短链生成 (URL) 要拆分成两个服务？**
   - *回答要点*：读写 TPS 差异极大。跳转是极高频读（无锁），短链生成是相对低频写（涉及唯一性、DB保存）。独立部署以分配不同资源（Redirect 给更多节点实例），且防止生成接口的 OOM 或故障拖垮核心跳转响应。
2. **API 网关在这个系统中做了什么？**
   - *回答要点*：统一鉴权（JWT/Token，区分哪些是用户生成 API）、请求路由、全局限流（针对单个 IP 的高频创建请求或恶意点击请求）、熔断降级。
3. **内部调用为什么选 gRPC？Go-Micro 是怎么做服务注册与发现的？**
   - *回答要点*：gRPC 基于 HTTP/2 和 Protobuf，二进制序列化体积小，长连接多路复用，适合内部高频通信。Go-Micro 默认可用 Consul/Etcd 做注册中心，通过 Watch 机制实现服务节点变更的客户端负载均衡。

### 模块 2：发号器与短链生成系统（⭐️重点考察区）
4. **为什么不用 UUID 或 Snowflake 的 Hash 取前几位，而是用 Redis INCR？**
   - *回答要点*：UUID 和 Snowflake 生成的都是较长的字符串/自增数值，直接哈希取前几位**绝对会有哈希冲突**，遇到冲突需要循环查库重试，影响并发。由于短网址一般要求在 6-7 位以内，Base62 理论能支撑 `62^7 = 3.5万亿` 的绝对无冲突映射，INCR 是保证全局递增的完美方案。
5. **追问：Redis INCR 挂了怎么办？会造成主键重复吗？**
   - *回答要点*：不要每次生成查一次 Redis。采用**预分配号段（Segment）机制**。比如每次从 Redis 拿步长为 1000 的区间存入内存，内存发完再请求。Redis 哪怕宕机重启，只要 AOF 恢复或者强行跳过几万 ID，依然保证全局唯一。这种方式减少网络 IO，进一步提升生成极速。
6. **你简历上说“降低连续 ID 可枚举风险”，你觉得普通 Base62 算法能防枚举吗？**
   - *回答要点*：（一定要指正自己）普通 Base62 无法防枚举（1->a, 2->b，黑客能推测出业务量）。我使用的方法是：① 扰乱 Base62 的字符表序列（打乱 0-9，a-z, A-Z 的顺序）；②（更高级）发号器发出的 ID 不是直接转换，而是借助跳跃比特位，或者类似 块加密（Feistel 结构）将其可逆地随机化，然后再做 Base62，这样看着就像纯随机串。
7. **用户自己瞎写了一个 Alias（自定义短码），恰巧和你 INCR 生成出来的 base62 码碰撞了怎么办？**
   - *回答要点*：数据库和生成逻辑切分命名空间。例如，用户自定义的固定 8 位以上，系统生成的固定 6/7 位；或者存储时发现唯一键冲突表报错，通过捕获唯一约束错误返回给前端提示“别名已存在”。

### 模块 3：高并发跳转链路 (Redirect)（⭐️核心技术亮点）
8. **描述一下网关拦截到 "http://t.cn/XyZ123" 后的完整生命周期？**
   - *回答要点*：Nginx -> Gateway 路由 -> Redirect Svc -> 解析 Path -> L1 缓存检索 -> Bloom Filter 防穿透 -> L2 (Redis) 检索 -> Singleflight 保护 -> PostgreSQL -> 数据组装构建响应（302） -> 投递点击事件至 NATS -> 结束返回。
9. **为什么使用 302 而不是 301 重定向？**
   - *回答要点*：301 是**永久重定向**，浏览器会把目标地址缓存在本地硬盘里。下次用户再点击短链，浏览器直接跳走，不会再向我们的服务器发请求。这样我们就彻底**丢失了分析数据（PV/UV统计失效）**。使用 302（或 307）保证每次点击必须经过我们的服务器。
10. **L1 本地缓存和 L2 Redis 会有数据一致性问题吗？**
    - *回答要点*：由于短链接口一般是**“创建后基本上不修改”**的，且短链接允许一定的延迟可见。如果需要修改（例如封禁违规短链），可以通过 Redis Pub/Sub 给 Redirect 实例广播 invalidate 消息来让 L1 本地缓存失效；或者给 L1 设置一个较短的 TTL（比如 30 秒）。
11. **如何防止缓存击穿？具体谈谈 Singleflight 的底层实现。**
    - *回答要点*：防死热数据突然过期。大量相同短码请求进来，找不到 L1和L2。使用 Golang 的 `golang.org/x/sync/singleflight`。底层其实就是一个 `sync.Mutex` 保护的 map。第一个请求进去，在 map 登机等待执行 DB；后续进来的协程看到这架航班已经起飞，就通过 `sync.WaitGroup` 挂起阻塞等待，等第一个查回来之后，唤醒其他的直接复用查到的结果，只发生 1 次 DB IO。
12. **如何防缓存穿透？布隆过滤器怎么处理“短链已过期或被删”的情况？**
    - *回答要点*：黑客如果用不存在的短码库疯狂攻击，数据库会崩塌，所以上缓存前先查 Redis BloomFilter。因为布隆过滤器基于多次 Hash，底层是一串 BitMap，有几率多个 Key 命中相同的 Bit 位置，因此**标准布隆过滤器不支持删除被回收的短链**。
    - *应对策略*：短链过期其实通常在 Redis 存空值哨兵（有效期 5 分钟），即使过了布隆判断，在 L2 拿到空值也就挡回去了。
    - *替代策略*：或者使用 Cuckoo Filter（布谷鸟过滤器），支持删除；或者干脆不删，反正布隆只会返回 false positive，稍微漏过去一部分最后会被 DB 挡住，无伤大雅。

### 模块 4：异步解耦与削峰（NATS JetStream）
13. **为什么使用 NATS JetStream？相对于普通的 NATS 或者 Kafka 优势何在？**
    - *回答要点*：比起纯的 NATS，JetStream 提供了**持久化（Persistence）和 At-least-once 投递保证**。比起 Kafka，使用 Go 编写的 NATS 极其轻量化，部署运维成本极低，对于这种单纯的点击事件削峰完全足够，且吞吐量甚至在某些场景下高于 Kafka。
14. **Redirect-Svc 向 NATS 投递消息失败了（例如网络断开），如何保证高可用？会影响跳转主链路吗？**
    - *回答要点*：**核心是解耦和降级。** 投递必须是异步非阻塞的协程或带有极短 timeout 的机制，坚决不能让统计拖慢 302 返回。如果 NATS 投递挂了，兜底策略是写入本地主机的磁盘日志进行积压（Log-based fallback），等网络恢复由后台 Agent 利用 Filebeat 捞取重传补扫。

### 模块 5：海量数据存储与 ClickHouse（Analytics）
15. **跳转消息大量消费，怎么防止把 ClickHouse “写死”？**
    - *回答要点*：ClickHouse 极度不适合单条数据的极高频插入，会引起底层 `parts` 爆掉（Too many parts 错误）。在 Analytics-Svc 这一侧，利用 Go 的 channel 或第三方库（如 `go-zero` 的 batch executor）**攒批写入**（例如：每两秒收集 5000 条，或者缓冲区满 10000 条触发一次 bulk insert）。还可以结合 NATS 取消息时的 `FetchBackoff` 。
16. **NATS JetStream 保证至少一次（At-least-once），ClickHouse 里面出现了点击重复数据怎么办？**
    - *回答要点*：给每一次重定向生成一个唯一的 `TraceID（ClickID）`（在跳转服务生成）。在 CH 中建立表结构时，使用 `ReplacingMergeTree` 引擎按 `ClickID` 去重，或者后期通过在 CH 查询时用 `argMax` 取最后一条，亦或者干脆统计时用精确去重的 `uniqExact`。
17. **在 ClickHouse 里如何统计 PV、UV 和 TopN？（考察底层表设计）**
    - *回答要点*：建一张访问明细本地表（Local 表）加分布式表（Dist 表）。
      - PV 是 `count()`。
      - UV 使用 CH 提供的基数估算算法函数 `uniq` 或精确统计 `uniqExact(IP/UserID)`。
      - 为减少查询实时计算开销，使用 ClickHouse 的 **Materialized View (物化视图)** 搭配 `AggregatingMergeTree`，例如按天/按小时的 UV 聚合表，这样请求分析面板时瞬间就能拉出走势图。

### 模块 6：监控、部署与系统工程
18. **如果要在这个系统加入限流机制，你怎么设计？**
    - *回答要点*：
      - 在 API Gateway 层：对 `生成短链接口` 基于 Token/UID 做 Lua 脚本实现的 Redis 令牌桶限流，限高频刷量。
      - 对 `跳转短链接口` 依据 IP 限流（防爬虫乱点击）。
19. **压测环境 QPS 最高 1676 时，当时的瓶颈究竟出现在哪里？**
    - *回答要点*：（这需要你自己回想测试过程，常见答案是）如果是单体 1 台物理机跑 Docker，瓶颈可能是 Docker 的网络 NAT 转发损耗；或者是压测客户端到网关的 TCP 连接端口迅速用光导致 TIME_WAIT；如果排除了网络，那一定是短链找不到 L1，全部打到 Redis 获取或者落到 PostgreSQL 然后单机并发连接数被耗尽拉高了延迟。
20. **Jaeger 分布式追踪里，Span ID 和 Trace ID 是如何在 gRPC 之间和 NATS 之间传递的？**
    - *回答要点*：通过 Context。在 gRPC 中就是将 Trace ID 放进 Metadata 里透传给下游。抛进 NATS 消息队列时，需要把 Trace Context 序列化放进 Message Header 中，Analytics-Svc 消费时再反序列化并注入其当前上下文接着上报，这样链路在 Jaeger UI 上才连得起来。

## 终极高光“坑点”准备（面试亮点）

当面试官问你：“在这个项目中，你遇到过最大的困难是什么？怎么解决的？”
请选择以下其中一个讲成一个故事：

> **故事板 A：应对缓存击穿引发的灾难**
> “刚开始压测的时候，我制造了一个‘瞬时大V发博’的场景：让压测脚本带着完全相同的 1 个新建短码瞬间涌入几千并发。我发现 DB 连接立马飙满了！我追踪下去发现是因为刚创建的短链还没热度，L1 不存在，全部瞬间穿透到了 Redis 和 PG。这就引出了我后来使用 golang.org/x/sync/singleflight 的过程。加入 singleflight 后，所有的几千个并发锁在了 Redirect 层面，最终只有一个协程去请求了 Redis 并回填，PG 的请求量归零，P99 延迟极大降低了。”

> **故事板 B：ClickHouse 小文件合并风暴（Too many parts）**
> “我在联调 NATS 到 Analytics 消费数据写入 ClickHouse 的过程中，为了实时看到日志，我让 NATS 的消费者一条一条直接 `insert` 进 DB。几分钟后，几万并发量直接把 ClickHouse 跑出 ‘Too many parts’ 报错宕机了。查阅文档后我深刻理解了列存型 OLAP 的特性，立刻重构了消费端的逻辑，自己用 Golang 的 slice 和 channel 写了一个简单的异步环形缓冲池（Batcher），每积攒够 5 满秒或 10000 条目，再向 ClickHouse 执行一次批量 Insert 操作，瞬间就跑顺了。”

> **故事板 C：防止竞品爬虫恶意枚举**
> “最开始设计短链时我就想到了安全问题。一开始我觉得用 ID 自增配合 Base62 很优雅。但测试时我发现：今天我是 /a，第二天变成了 /z。竞争对手只要定时爬取，就能把我的平台单量完完整整地监控到。后来我在 ID 到 Base62 转换之间，引入了一个简单的 Feistel 密码混淆（或者跳位混淆），出来的结果表面呈完全无规律散列态，彻底堵死了枚举漏洞，且依然能保持完美的强碰撞避免及唯一性。”
