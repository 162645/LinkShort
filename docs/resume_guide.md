# 简历与面试指南：Go 分布式短链接系统

本文档旨在指导您如何在简历中描述该项目，以及如何回答与设计相关的常见面试问题。

## 1. 简历项目描述

请根据您简历的版面空间选择最合适的描述方式。

### 选项 A：精简版 (项目经历)
**项目：基于 Go 微服务的高性能分布式短链接系统 (Redis, ClickHouse)**
*   设计并实现了一个基于 **Go Micro** 和 **NATS** 的分布式短链接平台，单机 QPS 达到 **5,000+**，P99 延迟稳定在 **<2ms**。
*   构建了**多级缓存架构**：引入 **L1 本地缓存 (Go-Cache)** 与 **L2 分布式缓存 (Redis)**，大幅降低数据库 IO 压力。
*   实现了基于 **Redis 原子计数器 + 乱序 Base62 编码** 的分布式 ID 生成策略，实现 100% 冲突率抵御并保证短码无规律。
*   首创缓存防护体系：集成 **布隆过滤器 (Bloom Filter)** 拦截非法请求（防穿透），使用 **Singleflight** 合并突发热点请求（防击穿）。
*   集成了完整的可观测性技术栈 (**Prometheus, Grafana, Jaeger**)，实现了对系统瓶颈的精准监控和全链路追踪。

### 选项 B：详细版 (STAR 法则)
**项目：企业级短链接服务平台**
*   **挑战**: 构建一个能够应对高流量尖峰的短链接系统，要求生成唯一的短码，并提供实时数据分析，同时不能影响重定向服务的性能。
*   **架构**: 采用微服务架构，将读密集型（重定向）和写密集型（数据分析）的负载进行了物理分离。
*   **关键实现**:
    *   **缓存策略**: 实施了 Redis 缓存并配合**布隆过滤器**防止缓存穿透，针对热点链接实现了 **100% 的缓存命中率**。
    *   **数据管道**: 基于 NATS 构建了事件驱动的分析管道。访问日志被异步推送到 ClickHouse，查询聚合速度比传统行式数据库快 100 倍。
    *   **性能优化**: 调优了 Redis 连接池和 Go 运行时配置以减少 GC 停顿，将平均延迟稳定在 **~4.5ms**。
*   **结果**: 通过 wrk 压测成功验证了系统在高负载下的稳定性，实现了稳定的 QPS 和零数据丢失。

## 2. 面试 Q&A 准备

### Q1: 为什么选择微服务而不是单体架构？
**回答**:
“虽然单体架构起步简单，但我预见到系统的不同部分有截然不同的扩展需求。**重定向服务**是读密集型的，需要大量复制实例来抗并发；而**分析服务**是写密集型的，受限于磁盘 I/O。通过微服务拆分，我可以独立扩展重定向服务来应对流量高峰，而不会浪费资源在分析组件上。此外，这提供了更好的故障隔离——即使分析服务挂了，用户的重定向功能依然正常。”

### Q2: 为什么用 ClickHouse 做分析？为什么不用 PostgreSQL？
**回答**:
“PostgreSQL 是行式存储，非常适合事务性数据（ACID），但在处理数百万行数据的聚合查询（例如‘统计某链接的日点击量’）时效率很低。**ClickHouse** 是专为 OLAP 设计的列式数据库。它支持极高的写入速度（每秒数百万条），并且可以在毫秒级扫描数十亿行数据用于报表生成，这对于实时仪表盘功能至关重要。”

### Q3: 你是如何生成唯一短码的？
**回答**:
“我避免了‘生成随机串 + 查库去重’的低效做法，因为随着数据量增加，这会导致严重的性能下降和竞态条件。我采用了**Base62 编码**唯一 ID 的方案。ID 通过分布式机制（如 Twitter Snowflake 或 Redis `INCR`）生成。这在数学上保证了全局唯一性，实现了零冲突，并消除了生成过程中对数据库唯一性检查的依赖。”

### Q4: 你是如何处理“缓存雪崩、穿透与击穿”的？
**回答**:
“针对**缓存穿透**（查询不存在的 Key），我使用了**布隆过滤器 (Bloom Filter)**，在不访问数据库的情况下拦截 99% 的恶意流量。针对**缓存击穿**（热点 Key 失效时的并发冲击），我利用了 **Singleflight** 技术，将同一时刻针对同一短码的多个数据库调用合并为一个，极大保护了后端存储。此外，通过 **L1 本地缓存** 进一步缓冲了极热点 Key 对分布式缓存 Redis 的瞬时压力。”

### Q5: 如果分析服务宕机了会发生什么？
**回答**:
“由于系统使用 **NATS** 进行异步消息传递，重定向服务只需发布事件即可继续处理，不需要等待响应。如果分析服务宕机，NATS（配合持久化/JetStream）会缓存这些消息。一旦服务恢复上线，它会消费积压的消息。这种设计确保了用户的重定向体验具有高可用性，不会受后台组件故障的影响。”
