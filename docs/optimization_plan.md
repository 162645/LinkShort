# 项目优化建议方案

基于当前代码实现的审查，本项目虽然在架构上实现了微服务拆分和读写分离，但在高并发、海量数据场景下仍有显著的优化空间。

## 1. 核心优化：短码生成策略 (ID 生成器)

### 当前现状
目前使用的是 **“随机字符串 + 数据库查重”** 的方式。
*   **问题**: 随着数据库中短码数量的增加，生成随机码时发生冲突的概率会指数级上升。这将导致多次数据库查询（重试），严重拖慢写入性能。
*   **瓶颈**: 数据库的唯一索引检查成为写操作的瓶颈。

### 优化建议：引入分布式 ID 生成器
建议废弃随机生成策略，改用 **ID 生成算法 + Base62 编码**。

#### 方案 A: Snowflake 算法 (推荐)
*   **原理**: 使用 Twitter 的 Snowflake 算法生成全局唯一的 `int64` ID。
*   **优点**: 
    *   **零冲突**: 算法保证生成的 ID 全局唯一，**无需查询数据库查重**。
    *   **高性能**: 本地计算，无需网络 I/O，单机可达数百万 ID/秒。
    *   **有序性**: ID 按时间大致有序，有利于数据库索引性能。
*   **实施**: 引入 Snowflake 库，生成 ID 后进行 Base62 编码即可得到短码。

#### 方案 B: Redis 自增 ID
*   **原理**: 利用 Redis 的 `INCR` 原子操作生成连续 ID。
*   **优点**: 简单易实现，严格递增。
*   **缺点**: 依赖 Redis 可用性；ID 连续可能被遍历预测（安全性稍差）。

## 2. 核心优化：缓存系统增强

### 当前现状
目前仅使用了简单的 **Redis Key-Value 缓存**。
*   **问题 1 (缓存穿透)**: 如果恶意用户大量请求不存在的短码，请求会穿透 Redis 直接打到数据库，可能导致数据库崩溃。
*   **问题 2 (缓存击穿)**: 某个热点 Key 过期时，大量并发请求会同时访问数据库。

### 优化建议

#### 2.1 引入布隆过滤器 (Bloom Filter)
*   **原理**: 使用布隆过滤器存储所有已存在的短码。
*   **流程**: 
    1. 请求到来 -> 2. 查布隆过滤器 -> 3. 如果不在，直接返回 404 (拦截) -> 4. 如果在，查 Redis -> 5. 查数据库。
*   **效果**: 哪怕有 1 亿次恶意请求，绝大多数都会被布隆过滤器拦截，极大保护数据库。

#### 2.2 使用 Singleflight (防击穿)
*   **原理**: 对同一个 Key 的并发请求，在处理过程中（查库+回填缓存）合并为一个。
*   **效果**: 即使 1 万个请求同时访问同一个过期的热点 Key，也只会有一个请求打到数据库，其他请求等待共享结果。

#### 2.3 多级缓存 (Local Cache + Redis)
*   **建议**: 在 `redirect-svc` 进程内存中引入本地缓存 (如 BigCache 或 FreeCache)。
*   **效果**: 对于极热点的短链接（如头部 1% 的流量），直接内存返回，连 Redis 网络开销都省了，延迟可降至微秒级。

## 3. 其他架构优化

### 3.1 数据库读写分离 (主从架构)
*   **建议**: 部署 PostgreSQL 主从复制 (Master-Slave)。
*   **实施**: `url-shortener-svc` 写主库，`redirect-svc` 读从库。
*   **效果**: 进一步提升读取性能，将读压力从主库分流。

### 3.2 静态资源 CDN 加速
*   **建议**: 如果短链接服务包含跳转中间页（如下载提示页），应将 HTML/CSS/JS 托管至 CDN。

### 3.3 连接池调优
*   **建议**: 根据压测结果精细化调整 Redis 和 PostgreSQL 的连接池参数（`MaxOpenConns`, `MaxIdleConns`, `ConnMaxLifetime`），避免在高并发下因连接频繁创建销毁带来的开销。
